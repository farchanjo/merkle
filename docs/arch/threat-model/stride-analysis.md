# STRIDE Analysis

**Project:** Merkle — local-first MCP vault  
**Version:** 0.1.0  
**Scope:** All components in the deployed topology (vault-agent daemon, MCP server
adapter, MCP client, SQLite database, audit log, keychain backend, companion
socket, backup file, external services, remote audit webhook)  
**Methodology:** STRIDE per component. Each row enumerates 3–5 substantive threats
where the category applies; `N/A` is stated with a reason where a category
genuinely does not apply.

Risk levels: **Critical**, **High**, **Medium**, **Low**.

---

## 1. VaultAgent (daemon)

The long-running background process that owns key material, the domain core, the
audit log, and every secret operation. Highest-trust component; compromise yields
everything.

| STRIDE | Threat | Attack Vector | Impact | Mitigation | Residual Risk |
|---|---|---|---|---|---|
| Spoofing | A rogue local process claims to be a legitimate MCP server when connecting to the agent over the companion socket. The agent might grant it access to Use Token resolution. | Local attacker with user privileges; or a maliciously injected library in a client process spawns a second companion socket client. | Full secret disclosure for any namespace bound to the session. | Companion socket authenticates callers by PID + resolved process name against the `allowed_consumers` glob list; the process binary path is resolved via `/proc/<pid>/exe` (Linux) or `proc_pidpath` (macOS) and compared against the allowlist. | Medium — TOCTOU between PID lookup and subsequent calls; mitigated by checking on every request, not only at connection open. |
| Spoofing | An attacker replaces the `vault-agent` binary on disk (supply chain or local write) before the next boot, so that when the system restarts, the replaced binary impersonates the real agent. | Local attacker with write access to the installation path; or a compromised software update pipeline. | The fake agent captures secrets, master key wrapping requests, and audit data. | Binary is installed to a path owned by root (`/usr/local/bin`); macOS Gatekeeper + code signing; launchd plist runs as the user with restricted file ownership on the install path. | High without code signing; Medium with notarized + hardened runtime. |
| Spoofing | An adversary crafts MCP JSON-RPC messages that spoof a `session_id` belonging to a different user session to access that session's bound namespace. | Local attacker with user privileges capable of observing the stdio pipe or guessing a UUIDv7 value. | Cross-session namespace confusion; possible disclosure of a sibling session's secrets. | Session IDs are UUIDv7 (128-bit random component); not predictable across sessions. Agent binds session to the connecting PID and checks on every call. | Low — UUIDv7 has sufficient entropy; cross-session access requires knowledge of the session ID. |
| Tampering | A local attacker with user privileges sends forged JSON-RPC requests to the agent's companion socket (e.g., `vault.delete` or `vault.rotate`) to destroy or corrupt secrets. | Same Unix UID as the running agent; companion socket permissions are `0600`. | Irreversible secret deletion; secret rotation to attacker-controlled values. | Operations that mutate secrets require the caller to appear in the `allowed_consumers` list for the namespace; destructive operations (`delete`, `rotate`) require Operator Confirmation; audit entry is emitted before mutation is applied. | Medium — if the attacker's process is already on the allowlist (e.g., the Claude Code process was hijacked). |
| Tampering | A prompt injection payload instructs the LLM to call `vault.use` repeatedly with different purposes, exhausting rate limits or forcing writes of arbitrary purpose strings into the audit log. | Malicious content in a file, web page, or API response processed by the LLM. | Rate limit exhaustion; audit log pollution that obscures real forensic events. | Per-class rate limits enforced in the agent, not the MCP adapter; purpose string is bounded in length and validated against a safe charset; rate limit violation itself is an audited event. | Low — rate limits make exhaustion expensive; audit pollution visible in chain. |
| Tampering | A local root attacker injects a shared library into the agent process (via `LD_PRELOAD` or macOS dyld), replacing cryptographic routines to extract key material. | Root-level attacker on the same host. | Complete key hierarchy extraction; all secrets compromised past and future. | macOS: hardened runtime disables `DYLD_INSERT_LIBRARIES` for notarized binaries; System Integrity Protection protects process memory. Linux: `PR_SET_DUMPABLE=0`; consider `landlock` + seccomp filter on the agent. | High on Linux without kernel-level isolation; Medium on macOS with hardened runtime. |
| Repudiation | The agent process crashes or is killed mid-operation, leaving the audit log in an inconsistent state where an operation was performed but not recorded. | Crash induced by memory exhaustion, SIGKILL, or power loss. | Unrecorded secret access; breaks the chain verifier. | Audit entry is written to the append-only JSONL and SQLite mirror before the operation is executed (pre-commit audit); both use SQLite WAL transactions for atomicity. | Low — crash between audit write and op execution means the record exists but the op might not; this is the safer failure mode. |
| Repudiation | The operator (or an attacker with operator access) claims that a secret was never accessed, but the LLM extracted it via a proxy tool. | Trusted insider; or attacker who compromised the operator's session. | Denial of access events in breach investigations. | Audit entries are chained by Blake3 hash; every `vault.use` and `vault.ssh.exec` is recorded with caller PID and session ID; HMAC signature enables third-party verification via remote sync. | Medium — chain only covers what was logged; if the agent itself is compromised, entries may be fabricated. |
| Info Disclosure | Key material held in agent memory is exposed via a core dump on crash or via `/proc/<pid>/mem` access by a root process. | Local root attacker; or unintentional coredump to a world-readable path. | Master Key, Vault Root Key, or plaintext secrets disclosed. | Memory pages holding key material are `mlock`ed and zeroed on drop (Zeroize trait); coredumps disabled via `PR_SET_DUMPABLE=0` (Linux) and equivalent on macOS; crash handlers do not capture heap. | Medium — OS-level protections are best-effort; a kernel exploit bypasses them. |
| Info Disclosure | Plaintext secret material leaks through the process's environment variables or command-line arguments when the agent spawns child processes (e.g., external SSH subprocess). | Local attacker reading `/proc/<pid>/environ` or `ps aux`. | Plaintext credential exposure to any local process with user read permission. | Secrets injected into spawned processes via environment are cleared from the agent's own env before exec; child processes use `PR_SET_DUMPABLE=0`; environment variable injection uses explicit `env` list, not inherited parent env. | Medium — child env is visible briefly during exec on Linux before exec clears it. |
| Info Disclosure | A timing side-channel in the HMAC comparison for Companion Socket authentication allows a local attacker to forge an authentication token byte-by-byte. | Local attacker able to make repeated rapid authentication attempts. | Companion socket authentication bypass. | HMAC comparison uses constant-time `subtle::ConstantTimeEq`; connection rate limiting bounds attempt frequency. | Low — constant-time comparison eliminates the timing channel. |
| DoS | A local attacker floods the agent's companion socket with connection requests or malformed JSON-RPC messages, consuming all file descriptors or CPU. | Local attacker with user privileges. | Agent becomes unresponsive; no secrets accessible; backup scheduler stops. | Per-client connection limit and per-second message rate limit enforced in the socket acceptor; malformed messages are rejected with minimal parsing work (length prefix validation before deserialization). | Low — resources bounded. |
| DoS | A memory exhaustion attack sends crafted JSON-RPC payloads with extremely large `purpose` or `handle` strings, causing the agent's allocator to fail. | Local attacker via MCP adapter (through prompt injection). | Agent OOM; sealed state forces manual unseal; potential data loss if WAL not flushed. | All string fields have a maximum byte length validated before allocation; the MCP adapter enforces JSON message size limits before forwarding to the agent. | Low — bounded inputs. |
| Elevation of Privilege | A prompt injection payload constructs a `vault.spawn` call with `env` variables containing injected shell metacharacters, causing the spawned process to execute attacker-controlled commands. | Malicious content processed by the LLM. | Arbitrary command execution under the user's account. | `vault.spawn` builds the `argv` list directly without a shell; environment variable names and values are validated against a safe charset; no shell interpolation occurs; the spawned command must appear in a per-namespace allowlist. | Medium — allowlist enforcement depends on operator configuration. |
| Elevation of Privilege | A bug in the agent's JSON-RPC deserialization allows type confusion that causes a `vault.list` call (read-only) to be internally treated as a `vault.delete` call (destructive). | Local attacker or prompt injection via any LLM call. | Irreversible secret deletion without Operator Confirmation. | Strict enum-based dispatch from the tool name; no dynamic method resolution; each operation has an independent code path; integration tests cover all tool-to-handler mappings. | Low — strict dispatch removes ambiguity. |

## Amendment — 2026-05-22

### New STRIDE Entries

#### A. cross_env_warning Event

The `cross_env_warning` event is emitted by the agent when a tool call argument
contains a `handle` URI that references a namespace other than the namespace bound
to the current MCP session (cross-environment namespace access).

| STRIDE | Threat | Attack Vector | Impact | Mitigation | Residual Risk |
|---|---|---|---|---|---|
| Spoofing | A prompt injection payload crafts a `vault.use` call with a `handle` URI from a namespace the current session is not bound to, attempting to access secrets outside the session's scope. | Malicious content in LLM context; adversarially crafted handle URI. | Cross-namespace secret disclosure if the namespace boundary check is not enforced. | The agent checks the namespace field of every handle URI against the session's bound namespace list before dispatching; unbound namespaces are rejected with `NAMESPACE_NOT_BOUND`; the rejection emits a `cross_env_warning` audit entry including the attempting session ID and the target namespace. | Low — namespace binding is enforced at the agent, not the adapter. |
| Tampering | An operator misconfigures a `.merklerc` to include a `namespace_bind` override that adds an unintended namespace to the session, widening the attack surface for prompt injection. | Attacker-controlled `.merklerc` in a project directory. | Session gains unintended access to a sensitive namespace. | Security profile settings in `.merklerc` can only restrict, not widen, the namespaces bound by the global `config.toml`; an attempt to bind a namespace not listed in the global config emits a `cross_env_warning` and is rejected. | Medium — depends on correct `.merklerc` restriction enforcement. |
| Information Disclosure | A `cross_env_warning` audit entry itself discloses the target namespace label that was attempted, revealing that such a namespace exists. | Local attacker with read access to the audit log. | Namespace label discovery without actual secret access. | The `cross_env_warning` entry records the attempted namespace label (since the label is already in the handle URI, no new information is added beyond what the attacker already supplied); the entry does not include any secret metadata from the target namespace. | Low — audit entries are mode `0600`; attacker already knows the namespace label from their own crafted payload. |
| Information Disclosure | A cross-environment access event in a `dev` session leaks production handle naming conventions (namespace labels, category strings, secret name patterns) to the development toolchain or to any tool that receives the LLM's context. | LLM session bound to a `dev` namespace processes a document or API response that causes it to call `vault.use` with a `prod`-scoped handle URI; the resulting `cross_env_warning` audit entry and the rejected request both appear in the LLM's conversation transcript. | Production handle naming taxonomy (namespace labels, handle path structure, secret categorization) is disclosed to developer-tier tools and logs, enabling targeted spear-phishing or more precise future attacks against production secrets. | The `cross_env_warning` entry in the agent's audit log is mode `0600` and not returned to the LLM context; the rejected response to the LLM contains only the `NAMESPACE_NOT_BOUND` error code, not the target handle or namespace details; operator should use opaque handle aliases in dev namespaces for secrets that shadow production handles. | Medium — error code alone leaks no production data, but the original crafted handle URI (which the LLM already has) reveals the naming convention; residual risk is the LLM context window itself. |
| Tampering | An attacker with write access to the agent process (or via a supply-chain compromise of the vault binary) suppresses `cross_env_warning` audit events, hiding policy violations from compliance dashboards and SIEM integrations that monitor cross-environment access patterns. | Compromised vault-agent binary; or a root attacker patching the process in memory (Linux `ptrace`, macOS without SIP); or a crafted `.merklerc` or policy config that silently reclassifies the cross-namespace access as permitted. | Cross-environment access violations go undetected; a persistent attacker who uses cross-namespace access to exfiltrate secrets avoids triggering compliance alerts. | `cross_env_warning` events are written to the audit chain before the rejection is returned to the caller (pre-commit audit pattern); the hash chain would show a gap at the sequence number where the suppressed event should appear; the remote audit webhook (if enabled) would not receive the expected event, detectable by the webhook operator; the agent binary is protected by macOS Gatekeeper and code signing. | Medium — event suppression requires binary-level compromise or root access; detectable via chain gaps and remote webhook divergence; residual risk on systems without code signing. |

#### B. OOB Device Enrollment Threats

These threats arise from the companion device enrollment ceremony introduced in
ADR-0011 Amendment — 2026-05-22.

| STRIDE | Threat | Attack Vector | Impact | Mitigation | Residual Risk |
|---|---|---|---|---|---|
| Spoofing | An attacker who briefly gains access to the vault (e.g., physical access during a session) enrolls a rogue Ed25519 keypair as a companion device; thereafter the attacker can approve OOB challenges from their own device. | Physical access to a logged-in machine with an unsealed vault; or a compromised session. | Attacker can unilaterally approve `sensitivity=high` reveals without the operator's knowledge. | Device enrollment (`merkle device pair`) requires the vault to be unsealed AND requires operator presence at the TTY; enrollment is recorded as a high-priority `device_enrolled` audit entry including the device-id and the enrolling session's PID; the operator should review enrolled devices regularly with `merkle device list`; revocation is available via `merkle device revoke`. | High if the operator does not monitor enrolled devices; Medium with periodic review. |
| Tampering | An attacker swaps the enrolled Ed25519 public key stored in the OS keychain (or the vault's sealed state) with their own public key, enabling their device to sign challenge responses in place of the legitimate device. | Write access to the OS keychain entry holding the device's public-key fingerprint; or write access to the encrypted database + knowledge of the Master Key (to re-seal). | Attacker device can subsequently approve `sensitivity=high` reveals. | Keychain entries for enrolled device public keys carry a SHA256 fingerprint that is also recorded in the audit chain at enrollment time; `merkle doctor` compares the live keychain fingerprint against the audit-chain record and flags any mismatch as a `device_key_mismatch` warning; AEAD authentication on the sealed state detects unauthorized re-sealing. | Medium — requires either keychain write access or Master Key compromise; detected by doctor on next run. |
| Repudiation | A rogue enrolled device signs an `outcome=approved` challenge for a reveal the operator did not intend; the operator disputes the approval. | Enrolled-but-rogue device; insider threat. | Reveal occurred with a valid signature; operator claims non-repudiation. | The `oob_approved` audit entry records the `device_id`, the `challenge_id`, and the raw Ed25519 signature bytes; the public key on record proves which device signed; the enrolled-device audit entry proves the operator enrolled that device; any third party with the public key can independently verify the signature. | Medium — device-level non-repudiation is verifiable by any third party; individual-operator attribution requires the operator to protect the device's private key. |
| Information Disclosure | A compromised Companion Device displays the secret handle, namespace label, and sensitivity level on its screen during the OOB challenge UI, leaking this information to anyone with physical sight of the device. | Shoulder-surfing; screen-capture malware on a general-purpose phone acting as the Companion Device. | Secret handle naming patterns, namespace taxonomy, and sensitivity classification disclosed to an observer. | The Companion Device is recommended to be a dedicated security device (YubiKey-class hardware token) rather than a general-purpose phone with arbitrary app surface; challenge payloads on general-purpose devices should display only the minimum information needed for the operator to make an informed decision (challenge ID + sensitivity level only, not the full handle). | High if the Companion Device is a general-purpose smartphone — documented as residual risk; mitigated by using dedicated hardware. |
| Denial of Service | An attacker who can observe the OOB channel floods the Companion Device with `oob/challenge/issued` events, draining the operator's attention and making it difficult to distinguish legitimate from fabricated approval requests. | Local attacker with write access to the Companion Socket event stream; or a compromised session issuing `vault.reveal` calls in a rapid loop. | Operator approves a malicious challenge while trying to dismiss a flood of spurious ones; or the operator locks the device in frustration, blocking legitimate reveals entirely. | ADR-0011 rate-limit policy enforces `per_minute` and `per_hour` caps on OOB challenge issuance; challenges beyond the cap are rejected at the agent with a `rate_limit_exceeded` audit entry before the event is emitted to the Companion Socket. | Low — rate limits make flooding expensive; residual risk is an operator who has raised the cap to an unsafe level. |
| Elevation of Privilege | A compromised Companion Device (malware on the enrolled phone) automatically approves every `oob/challenge/issued` event without requiring user interaction, silently authorizing all `sensitivity=high` reveals. | Malware installed on the Companion Device that intercepts the OOB challenge notification and signs the response without displaying it to the user. | All OOB-gated reveals are silently approved; the `sensitivity=high` barrier provides no protection. | The OOB protocol requires a per-challenge user touch or biometric authentication event on the Companion Device before the private key is used to sign the response; signed approvals are bound to a single `challenge_id` and are invalid for any other challenge; the agent verifies the nonce binding in the signature. | High if the Companion Device OS is fully compromised — documented as residual risk; mitigated by using tamper-resistant dedicated hardware (YubiKey, hardware security module) where the private key cannot be extracted by malware. |
| DoS | An attacker floods the OOB challenge endpoint with approval requests bearing invalid signatures, consuming the agent's signature verification CPU. | Local attacker; or compromised device sending malformed challenges. | Agent becomes unresponsive to legitimate OOB approvals. | Per-device and per-session rate limits are enforced on OOB challenge responses; signature failures for a given device-id trigger an exponential backoff before the next response from that device is processed; repeated failures emit a `device_auth_failure` audit entry. | Low — rate limits bound the CPU consumption. |

#### C. Argon2id Parameter Downgrade Attack

| STRIDE | Threat | Attack Vector | Impact | Mitigation | Residual Risk |
|---|---|---|---|---|---|
| Tampering | An attacker with write access to the vault database modifies the stored Argon2id parameters (`m_cost`, `t_cost`, `p_cost`) in the sealed state record to values below the minimum-hardness floor, enabling fast offline brute-force of the passphrase. | Local attacker with user-level access to `vault.db`; sqlite3 CLI or direct byte patching; or an attacker who writes a crafted `config.toml` that overrides the parameters used during a key-rotation operation. | With `m_cost=1, t_cost=1`, Argon2id completes in microseconds; the passphrase is crackable with commodity GPU hardware within hours or minutes. | The agent enforces a compile-time minimum-hardness floor (m≥65536, t≥3, p≥1) at unseal time as defined in [ADR-0005 Amendment — 2026-05-22](../adr/0005-argon2id-kdf-for-passphrase-fallback.md); any attempt to unseal with below-floor parameters is rejected with `argon2id_parameters_below_minimum`; the sealed state record is AEAD-authenticated so modifying parameters without the Master Key produces an authentication failure on read; `merkle doctor` reports the current Argon2id parameter hardness at every run and emits a `kdf_parameters_below_recommended` warning if parameters are above the hard floor but below the recommended baseline; every unseal operation records the actual `m_cost`, `t_cost`, and `p_cost` values as a structured field in the `unseal_succeeded` audit entry. | Medium — parameter floor + AEAD authentication prevents undetected tampering against an attacker who does not hold the Master Key; an attacker who holds both the database AND the Master Key can re-wrap with weakened parameters and re-seal; additionally, an attacker who can replace the `merkle doctor` binary itself can suppress the hardness report, leaving the operator unaware of a parameter downgrade that occurred in a previous session. |
| Elevation of Privilege | An attacker supplies a crafted `.merklerc` or `config.toml` that specifies low Argon2id parameters for new-key derivation (not the sealed state), hoping the agent will derive a new key under weak parameters during a key rotation operation. | Attacker-controlled config file in a project directory. | Future-derived keys (after rotation) use weak parameters; offline brute-force becomes feasible for the new key. | Parameters used for new derivations during `merkle key-rotate` or `merkle init` are clamped to the minimum-hardness floor before use; a `[kdf]` section in `config.toml` that specifies below-floor values is rejected with a fatal error at agent startup. | Low — floor enforced at derivation time regardless of config. |

Cross-reference:
ADR-0005 Amendment — 2026-05-22,
ADR-0011 Amendment — 2026-05-22.

## 2. McpServer (adapter)

The short-lived process spawned per client window. Translates MCP tool calls over
stdio into JSON-RPC messages to the VaultAgent via the Companion Socket. Relatively
untrusted boundary: it sees MCP requests from the LLM and forwards them.

| STRIDE | Threat | Attack Vector | Impact | Mitigation | Residual Risk |
|---|---|---|---|---|---|
| Spoofing | An attacker spawns a rogue MCP server process (with the same binary path) connecting to the agent's companion socket, claiming to represent a legitimate MCP session. | Local attacker with write access to the PATH or the ability to exec the `merkle-mcp` binary. | Attacker-controlled MCP server mediates all tool calls, can intercept responses including revealed secrets. | Companion socket allowlist includes the canonical binary path; PID is checked on every call, not just at connection time; the agent verifies that the connected process is the expected binary using OS-level path resolution. | Medium — binary path check is TOCTOU-vulnerable; strong mitigation requires code signing. |
| Spoofing | A prompt injection payload attempts to make the LLM call MCP tools with a forged `session_id` that belongs to a different client window, hoping to access a different namespace. | Malicious content processed by the LLM. | Cross-window namespace access if the agent fails to validate the session binding. | Session IDs are issued by the agent at MCP handshake and are UUIDv7; the agent binds each session ID to the originating socket connection and rejects calls using an ID from a different connection. | Low — session binding is enforced at the agent, not the adapter. |
| Tampering | A prompt injection payload causes the MCP server to forward a `vault.reveal` request with a crafted `operator_confirmed=true` flag set in the JSON body, bypassing the OOB confirmation check. | Malicious content embedded in a document processed by the LLM. | Plaintext secret returned through the MCP transport without genuine operator consent. | The `operator_confirmed` flag is only accepted when the request carries a slash-command signature (the MCP client sets a verified header that the LLM cannot directly fabricate); the agent validates the signature, not the flag value alone. | High if the signature mechanism is unimplemented; Medium once implemented. |
| Tampering | The MCP adapter process is compromised via a dependency confusion attack (a malicious Rust crate published to crates.io shadows an internal dependency) and modified to strip HMAC fields from audit relay messages. | Supply chain attacker publishing a crate with a higher version number than an internal crate. | Audit entries forwarded to remote webhook are unsigned, enabling tampering without detection. | Cargo lock file pins all dependency versions; `cargo-audit` runs in CI against the advisory database; `cargo-vet` enforces manual auditing of new dependencies; the agent signs audit entries independently of the adapter. | Medium — supply chain attacks are hard to fully eliminate; vetting reduces probability. |
| Repudiation | The MCP adapter crashes between receiving the LLM's tool call and forwarding it to the agent, so the tool call is neither executed nor recorded. | Network error, OOM, SIGKILL. | A tool invocation is silently dropped; no audit entry exists. | The adapter is stateless; if the agent does not receive a request, no operation occurs; idempotent retry by the LLM is safe; the absence of an audit entry for an expected operation is itself detectable. | Low — loss of the adapter means loss of the request, not silent execution. |
| Info Disclosure | The MCP adapter logs full JSON-RPC messages to a debug log file that is world-readable, including tool call arguments that contain handle URIs and purpose strings. | Local attacker reads the log file. | Handle URIs exposed (though not plaintext material); purpose strings may reveal usage patterns. | Debug logging is disabled in production builds; log files are created with mode `0600`; log level defaults to `warn`; handles are treated as sensitive in log filters. | Low — handles are opaque and do not contain plaintext. |
| Info Disclosure | Prompt injection causes the LLM to call `vault.describe` on every secret in every namespace, accumulating public metadata in the conversation transcript that could be exfiltrated by subsequent prompts. | Malicious content in a processed document. | Public metadata (secret names, tags, categories, descriptions) disclosed in the LLM context window. | `vault.list` pagination limits the number of results per call; rate limits apply to list and describe operations; the Namespace Policy can restrict which namespaces are accessible per MCP session. | Medium — public metadata by design does not contain plaintext, but accumulation of metadata is itself an information gain. |
| DoS | A prompt injection payload triggers a tight loop of `vault.use` calls (each creating a Use Token), exhausting the agent's token table and potentially the file descriptor budget if tokens are file-backed. | Malicious content processed by the LLM in a long-running session. | Agent resource exhaustion; Use Token resolution fails for legitimate callers. | Per-session Use Token limit (configurable, default 64 outstanding); expired tokens are reaped by a background task; rate limits on `vault.use` per session. | Low — bounded per session. |
| DoS | The MCP adapter is fed an extremely large JSON-RPC request (multi-megabyte `params` object) by a misbehaving client, causing excessive memory allocation before the payload is validated. | Local attacker or a compromised MCP client process. | Adapter OOM; client window loses vault access. | JSON-RPC message size limit enforced at the framing layer (default 1 MiB); payloads exceeding the limit are rejected before deserialization. | Low — size limit at framing layer. |
| Elevation of Privilege | A prompt injection payload calls `vault.spawn` with a process binary not on the namespace allowlist, and a bug in the allowlist checker treats a path with a null byte as matching any allowlist entry. | Malicious content processed by the LLM. | Arbitrary process execution. | Null bytes and path traversal sequences are rejected during argument validation before the allowlist check; process paths are canonicalized and compared as byte slices without shell interpretation. | Low — explicit canonicalization before comparison. |

## 3. McpClient (LLM host)

The Claude Code client process. Untrusted from the perspective of prompt injection;
trusted as the authenticated operator terminal for slash commands.

| STRIDE | Threat | Attack Vector | Impact | Mitigation | Residual Risk |
|---|---|---|---|---|---|
| Spoofing | Prompt injection causes the LLM to emit a slash command (`/merkle-reveal`) as synthesized text, attempting to trick the client into treating it as a genuine operator-issued slash command. | Malicious content in any document, web page, or API response processed by the LLM. | Unauthorized reveal of a high-sensitivity secret without genuine operator intent. | Slash commands are recognized only when they appear at the beginning of the user turn (not inside LLM-generated assistant turns); the MCP client enforces this at the parsing layer; the agent also expects the slash-command-verified flag only from the user turn. | Medium — depends on correct implementation of the client's turn-parsing logic. |
| Spoofing | A compromised LLM provider modifies the LLM's responses to include crafted tool calls that appear to come from the operator's instructions, turning the LLM into a remote-controlled exfiltrator. | Malicious LLM provider or MITM on the provider's API. | LLM systematically invokes `vault.use` + `vault.reveal` on targeted secrets. | Handle-default policy means the LLM sees URIs, not plaintext; `vault.reveal` requires operator confirmation; rate limits bound the number of reveal operations per session; remote audit webhook records all reveals for out-of-band review. | High — full-trust break in the LLM provider is catastrophic; residual risk is reduced by handle default but not eliminated. |
| Tampering | Prompt injection modifies the LLM's interpretation of a proxy tool's output (e.g., `vault.ssh.exec` stdout) to include attacker-controlled text that the LLM then acts on in subsequent steps. | Malicious output from a compromised SSH target or HTTP endpoint reflected back through the LLM context. | The LLM performs unintended subsequent actions using the injected context; potential chained exfiltration. | Proxy tool outputs are length-bounded before being returned to the LLM; the agent can be configured to truncate or redact stdout from external commands; the audit log records the full output for forensic review. | High — content injection via external command output is inherent to LLM-as-composer; rate limits and audit are compensating controls, not preventive. |
| Repudiation | The LLM client discards the conversation transcript after the session ends, removing evidence of what tool calls were made and what the LLM's reasoning was. | Normal operation or deliberate erasure by an attacker who gained access to the client. | Loss of forensic context for incident investigation. | All tool calls are audited at the agent, not in the client transcript; the audit log persists independently of the client and cannot be erased without breaking the hash chain. | Low — agent audit is independent of client state. |
| Info Disclosure | The LLM accumulates secrets disclosed by prior tool calls in its context window and then includes them in a subsequent request to the LLM provider, transmitting plaintext to the cloud. | Normal LLM operation after a reveal; or prompt injection that causes the LLM to summarize secrets. | Plaintext secret transmitted to the LLM provider's servers. | `vault.reveal` is the only mechanism that returns plaintext to the MCP transport; it requires operator confirmation; high-sensitivity secrets also require OOB confirmation; operator should use reveal only when the LLM genuinely needs the plaintext value. | High — once plaintext enters the LLM context, the vault cannot control what the LLM does with it; this is the designed residual risk of the reveal opt-in. |
| Info Disclosure | The LLM client stores the conversation transcript in a local file or cloud sync that is accessible to other users or processes on the machine. | Weak file permissions on the transcript; iCloud/Google Drive sync of the home directory. | Conversation history including any revealed secrets is exposed. | Merkle does not control client-side transcript storage; operators should configure client applications to store transcripts in user-only directories; OS-level home directory encryption mitigates sync exposure. | Medium — out of scope for Merkle to fully address. |
| DoS | A prompt injection payload causes the LLM to call vault tools in an infinite loop until rate limits fire, consuming the operator's LLM API quota and degrading session responsiveness. | Malicious content in a processed document. | API quota exhaustion; operator unable to continue working in the session. | Per-session rate limits at the agent terminate the loop; rate limit violation is an audited event; the operator can unseal revocation by killing the MCP server process. | Low — rate limits are the primary control. |
| Elevation of Privilege | The LLM client process has excessive OS permissions (e.g., no sandbox) and a prompt injection payload causes it to execute system commands directly without going through the vault's proxy tools. | Malicious content that exploits the client's tool-use capabilities beyond vault-scoped MCP tools. | Arbitrary command execution; bypasses vault's audit log entirely. | Merkle's threat model does not attempt to sandbox the LLM client; this is the responsibility of the client application's security posture; vault audit covers only vault operations. | High — out of scope; noted for operator awareness. |

## 4. SqliteDatabase

The persistence backend. Stores the encrypted secret blobs, metadata, namespace
definitions, key wrapping material, and an audit mirror. WAL mode for concurrent
reads.

| STRIDE | Threat | Attack Vector | Impact | Mitigation | Residual Risk |
|---|---|---|---|---|---|
| Spoofing | N/A | SQLite is a local file; it has no authentication surface. Spoofing is not applicable to a passive file-based store accessed only by the local agent process. | — | — | N/A |

| Info Disclosure | The HMAC key used to sign audit entries is embedded in the `config.toml` in plaintext, and `config.toml` is committed to a version control repository. | Developer accidentally commits the config file. | HMAC key disclosed; attacker can forge audit entries that appear authentic to remote receivers. | `config.toml` contains only the HMAC key reference (service identifier in the keychain), not the key material itself; the actual HMAC key is stored in the OS keychain under a distinct entry; `config.toml` is added to `.gitignore` by default. | Low — key material not in config file; `.gitignore` default. |
| DoS | An attacker floods the webhook endpoint with requests that trigger rate limiting on the server, causing the vault's audit delivery queue to grow unboundedly and eventually exhaust memory. | Network attacker targeting the webhook endpoint from outside. | Audit delivery queue memory exhaustion in the vault agent. | The delivery queue has a bounded capacity (configurable, default 10,000 entries); when the queue is full, older pending entries are dropped with a local warning log entry; the local JSONL log is unaffected. | Low — bounded queue; local log is the authoritative record. |
